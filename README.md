# シフト自動作成

キャリアショップ向けに、スタッフごとの戦力ポイントから月のシフト表を自動で作るブラウザアプリです。サーバーは不要で、データはブラウザ（localStorage）にだけ保存されます。

## 守る条件

- 毎日、出勤者の戦力ポイント合計が必要ポイント以上
- 「絶対」の希望休の日は出勤しない。「できれば」の希望休は、条件を満たせる範囲でなるべく叶える
- 連勤の制限（初期値は「制限しない」。「必要ポイントとスタッフ」の設定で「2連勤まで」にすると、3日連続では出勤しなくなり、前月末の連勤も引き継ぐ）
- イベント出勤の日は、その人を出勤扱い（連勤を制限しているときは連勤に数える）にし、店の必要ポイントには数えない。日数に決まりはなく、何日でも入れられる

## 使い方

```sh
npm run build    # 単体で開ける dist/shift.html を作る（配布用）
npm start        # http://localhost:8000 を開く（index.html を直接開いても動きます）
npm test         # 計算部分のテスト
npm run test:e2e # ブラウザでの操作テスト（要 Playwright。スタッフ追加・希望休・Excel出力・印刷など）
```

1. スタッフと戦力ポイント、必要ポイント（平日／土日祝など高めの日）を設定する
2. 「希望休の入力」でスタッフごとに3日まで選び、「絶」（絶対休み）か「△」（できれば休み）をボタンで切り替える。4日以上は「希望休を入れる」モードでセルをタップ（押すたびに 絶対→できれば→なし）
3. イベントに出る人がいれば、「イベント出勤の入力」でスタッフごとに日付を好きなだけ追加する（表のセルをタップして 絶対→できれば→イベント→なし と切り替えても入れられる）。表では紫の「イ」になり、Excelにも「イ」で出力される
4. 「自動作成」を押す。押すたびに条件を満たす別の案が出る
5. 「出勤を直す」モードで手直しすると、ポイント不足（連勤を制限しているときは3連勤も）がその場で表示される
6. 月の途中で変更が出たら、希望休などを直して「作成する範囲」で開始日を選び、「◯日以降を作り直す」を押す。選んだ日より前（表で薄く表示）は今の表のまま動かず、その日以降だけを組み直す。直前までの連勤や、すでに出勤した日数の偏りも考慮される
7. 完成したら「印刷」または「Excel」（画面の表と同じ見た目の .xlsx。戦力ポイントは載りません）でスタッフに共有する

土日と祝日（振替休日・国民の休日を含め、カレンダーどおり）は、必要ポイントが多めの日になります。日付をタップすると「高め／通常」を切り替えられます。必要ポイントの数字は日ごとに書き換えられます。

## データの同期（どの端末からでも同じデータを見る）

`firebase-config.js` の設定が空の間は、これまでどおりブラウザの中だけに保存されます。設定すると、専用アカウントでログインした端末どうしで、スタッフ・希望休・イベント・作成したシフトが自動で同期されます（保存先は Firebase の Firestore、無料枠で足ります）。

設定のしかた（最初の1回だけ）:

1. [Firebase コンソール](https://console.firebase.google.com/) でプロジェクトを追加する（名前は自由。Google アナリティクスは不要）
2. 「構築 → Firestore Database」でデータベースを作成する（ロケーションは `asia-northeast1`（東京）、モードは本番環境モード）
3. 「構築 → Authentication」で、ログイン方法の「メール / パスワード」を有効にし、「ユーザー」タブでこのアプリ専用のメールアドレスとパスワードのユーザーを1人追加する。あわせて「設定 → ユーザーの操作」で「作成（登録）を有効にする」をオフにすると、他の人がアカウントを作れなくなる
4. 「Firestore Database → ルール」に `firestore.rules` の内容を貼り付け（`あなたのメールアドレス` を手順3のメールアドレスに書き換える）、公開する。このルールで、そのアカウント以外はデータを読み書きできない
5. 「プロジェクトの設定 → 全般 → マイアプリ」でウェブアプリ（`</>`）を登録し、表示される `apiKey` と `projectId` を `firebase-config.js` に書いて公開する（この2つは秘密ではない）

ログインできるアドレスを増やすとき（同じデータを、別のアドレスのアカウントからも見られるようにする）:

1. 「構築 → Authentication → ユーザー」で、ユーザーを追加する
2. 「Firestore Database → ルール」の `request.auth.token.email in [...]` のリストに、そのメールアドレスを足して公開する（例: `in ['1人目のメールアドレス', '2人目のメールアドレス']`）。ルールに書かないと、ログインはできても保存・読み込みは拒否される

使い方:

- 開くとログイン画面だけが出て、**ログインするまでシフト表などの中身は画面に出ない**。ログインしたままにしておけば、次からは入力不要（ログアウトは画面上部のボタン。ログアウトすると、また中身が隠れる）
- 変更は自動でクラウドに保存される。画面上部に「同期済み」「保存中…」「未保存（通信できません）」などが出る。通信できない間もこの端末には保存され、戻ると自動で送られる
- 別の端末で変更した内容は、画面に戻ったとき（または開き直したとき）に読み込まれる
- 2台で同時に編集して衝突した場合は、クラウドの内容に合わせ、この端末の未送信の変更はブラウザ内に退避する（`shift-work-backup-v1`）

## 公開（GitHub Pages）

デフォルトブランチに反映されるたびに、`.github/workflows/pages.yml` がテストとビルドをして `dist/shift.html` を GitHub Pages に公開します。公開されるのはこのHTML1枚だけです。入力内容は各自のブラウザにだけ保存され、サーバーには送られません。最初の1回だけ、リポジトリの Settings → Pages → Build and deployment の Source を「GitHub Actions」にしてください。

## 計算のしくみ（`solver.js`）

「各人が何日連続で出勤中か（0〜2）」を全員分まとめた状態を使い、月末まで条件を満たし続けられるかを厳密に調べます。条件を満たす表があれば必ず見つかり、無ければ最初に破綻する日と、その日に出られる最大ポイントを返します。満たす表の中から、余剰ポイントと出勤日数の偏り（土日祝を含む）が小さいものを選びます。

途中から作り直す `solveFrom` は、固定する日までの末尾の連勤と出勤日数（`workBase`／`highBase`）を数えたうえで、残りの日だけを `solve` で解きます。

条件を増やすときは、`allowedMask`（その日に出られる人の制限）と `feasible` に足すのが基本です。スタッフは10人までを想定しています。
